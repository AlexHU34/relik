# Relik — эксплуатация и надёжность (runbook)

Этот файл — ответ на вопрос «как сделать, чтобы сервис отвечал почти всегда».
Здесь нет теории: только что проверить, чем померить, что нажать и что делать,
когда сломалось.

---

## 1. Что считается «работает»

| Метрика | Цель | Чем мерится |
|---|---|---|
| Доступность сайта (index.html) | ≥ 99,5% | `service_samples`, `tools/status.html` |
| Доступность REST/Auth | ≥ 99,5% | там же |
| Realtime-доставка | ≥ 99% | там же (WebSocket-проверка) |
| p95 ответа REST | < 600 мс | `service_status.rest_ms` |
| Первый запуск приложения | < 2,5 с (Wi-Fi), < 8 с (3G) | DevTools / `scripts/e2e.mjs` |
| Восстановление после сбоя | < 5 мин | журнал алертов Telegram |

> 99% = 7 ч 12 мин простоя в месяц. 99,9% = 43 мин. Без истории проверок
> процент — это самообман, поэтому сначала включаем замеры, потом оптимизируем.

---

## 2. Из чего состоит система

```
Браузер
  ├── статика  → GitHub Pages (alexhu34.github.io/relik)   ← резерв: Caddy на VPS
  ├── API      → Supabase (Postgres + Auth + Storage + Realtime), регион EU
  ├── звонки   → coturn на VPS (62.113.99.46, Beget, СПб)
  └── push     → relik-push на VPS (pull-модель, входящий HTTPS не нужен)
```

Слабые места по порядку: бесплатный Supabase (пауза через 7 дней простоя,
5 ГБ egress, 500 МБ БД) → отсутствие алертов → единственный адрес статики.

## 3. Что уже настроено

- `scripts/vps.sh` — coturn, firewall, swap, **watchdog** (раз в минуту поднимает
  упавшие `coturn`/`relik-push`) и **keep-alive Supabase каждые 5 минут** с логом
  `/var/log/relik-keepalive.log`.
- `scripts/push-service` — push + мониторинг: раз в минуту проверяет сайт, Auth,
  REST, Storage, Realtime и TURN; раз в 5 минут пишет срез в `service_samples`;
  при сбое двух проверок подряд присылает алерт в Telegram и второй — когда
  всё восстановилось.
- `tools/status.html` — публичная страница: живые проверки из браузера +
  история доступности за 24 часа.
- `scripts/relik-health.mjs` — то же из терминала/по cron (JSON, код возврата).
- `.github/workflows/health.yml` — внешняя проверка каждые 15 минут с
  инфраструктуры GitHub (сбой = упавший запуск + письмо владельцу репозитория).
- `scripts/mirror-static.sh` + `scripts/Caddyfile.relik` — резервная копия сайта
  на своём домене (обновляется каждые 5 минут из GitHub). Уже поднято зеркало:
  `https://relik.62-113-99-46.nip.io/` (DNS nip.io, TLS автоматический).
- `scripts/backup-db.sh` — ежедневный `pg_dump` (бэкап БД).
- `tools/health.html`, `tools/preflight.html`, `scripts/e2e.mjs` — проверки
  конкретного устройства и сквозного сценария.

## 4. Включить мониторинг (30 минут, 0 ₽)

### 4.1. Telegram-бот для алертов

1. В Telegram: `@BotFather` → `/newbot` → имя → получаете токен вида
   `123456789:AA...`.
2. Напишите своему боту любое сообщение (иначе он не сможет писать вам первым).
3. Узнайте chat_id:

```bash
curl -s "https://api.telegram.org/bot<ТОКЕН>/getUpdates" | grep -o '"chat":{"id":[-0-9]*'
```

4. На VPS добавьте в `/etc/relik-push.env`:

```ini
SUPABASE_ANON_KEY=sb_publishable_...   # проверки от имени клиента
TELEGRAM_BOT_TOKEN=123456789:AA...
TELEGRAM_CHAT_ID=123456789
ALERT_AFTER=2
```

5. Перезапустите и проверьте:

```bash
systemctl restart relik-push
curl -s localhost:8099/healthz | head -c 600
```

6. Тест алерта: временно поставьте в `MONITOR_FRONT` несуществующий адрес,
   подождите 2 минуты — должно прийти `🔴 Relik: сайт (GitHub Pages) не отвечает`.
   Верните адрес, перезапустите, дождитесь `🟢`.

### 4.2. История доступности

В Supabase → SQL Editor выполните `supabase/service_uptime.sql`.
Через 5 минут в `service_samples` появятся срезы, а `tools/status.html`
покажет «Доступность за 24 часа».

Если SQL не выполнить — приложение продолжит работать, просто без истории
(статус-страница честно об этом скажет).

### 4.3. Внешний наблюдатель (важно)

Агент на VPS не может сообщить, что **сам VPS** умер. Два способа закрыть это:

- **без регистраций** — workflow `.github/workflows/health.yml` уже в репозитории:
  GitHub Actions каждые 15 минут запускает `scripts/relik-health.mjs` с чужой
  инфраструктуры; при сбое запуск падает и GitHub пишет письмо владельцу
  репозитория (проверить: вкладка Actions → Health → Run workflow);
- **с графиком и SMS** — бесплатный UptimeRobot / BetterStack на
  `https://alexhu34.github.io/relik/tools/status.html` (интервал 5 мин,
  keyword «Статус») и на резервное зеркало.

Рекомендую включить оба: Actions почти ничего не стоит, а UptimeRobot даёт
независимую вторую точку зрения.

## 5. Читаем статус правильно

Откройте `https://alexhu34.github.io/relik/tools/status.html`.

| Строка | Плохо, если | Что делать |
|---|---|---|
| Страница приложения | > 2,5 с или FAIL | проверить GitHub Pages status, переключиться на зеркало |
| База (REST) | FAIL или > 3 с | Supabase status page, Usage, не превышен ли лимит |
| Авторизация | FAIL | Status page Supabase, ключи в `js/config.js` |
| Файлы (Storage) | FAIL | квота Storage / egress |
| Realtime | «не открылся» | Realtime выключен в проекте или сеть режет WebSocket |
| TURN на сервере | «не отвечает» | `systemctl status coturn`, порт 3478 |
| Бэкап БД | «нет» или > 30 ч | cron `backup-db.sh`, место на диске |
| Диск сервера | < 1 ГБ | почистить логи/старые дампы |
| Доступность 24 ч | < 99% | смотреть, какие именно срезы падали |

`curl -s localhost:8099/healthz` на VPS отдаёт те же проверки в JSON.

## 6. План аварий

### 6.1. «Сайт не открывается» (GitHub Pages)

1. Проверить, что файлы живы: `curl -I https://alexhu34.github.io/relik/index.html`.
2. Открыть https://www.githubstatus.com — если авария у GitHub, переключить DNS
   на зеркало (оно уже работает: `https://relik.62-113-99-46.nip.io/`).
   Свой домен красивее: `A-запись relik.домен.ru → 62.113.99.46`, TTL 300.
   Без своего домена можно просто дать людям ссылку на зеркало.

3. После восстановления GitHub вернуть A-запись (или оставить зеркало, если
   оно стабильнее у ваших пользователей).

### 6.2. «Supabase не отвечает»

1. https://status.supabase.com — если авария, ждать; клиент покажет кэш чатов
   и баннер, сообщения уйдут из outbox после восстановления.
2. Если проект **paused** (free-тариф): Dashboard → Restore. Это и есть главная
   причина апгрейда на Pro.
3. Если лимит egress: Dashboard → Usage. До конца месяца проект будет
   ограничен — выгрузить медиа или оплатить Pro.

### 6.3. «Сообщения не приходят, хотя всё зелёное»

Realtime. Проверить в статус-странице строку Realtime; на VPS:
`curl -s localhost:8099/healthz | grep realtime`. Частые причины: Realtime
выключен для `messages` (Database → Replication), протух JWT, сеть режет
WebSocket (тогда работает опрос раз в 15 с — это штатный фолбэк).

### 6.4. «Звонки не соединяются»

`systemctl status coturn`, `journalctl -u coturn -n 50`, `ss -lunp | grep 3478`.
Если UDP режут — в конфиге уже есть `?transport=tcp`. Watchdog поднимает
coturn в течение минуты сам.

### 6.5. VPS недоступен

- Статика: переключить DNS на GitHub Pages (обратная операция к 6.1).
- Звонки: без TURN останутся только сети без строгого NAT (STUN).
- Push: уведомления не приходят, сообщения — приходят.
- Мониторинг: алерт придёт от внешнего наблюдателя (4.3).

### 6.6. «Всё медленно, но работает»

Смотреть `rest_ms` в статусе. Если > 1 с стабильно:
- проверить регион проекта (Settings → General → Region): для РФ лучше
  eu-central / eu-west;
- проверить, не включён ли VPN у пользователя;
- на клиенте: DevTools → Network → количество запросов (сейчас ~64 модуля,
  кэшируются SW; первый запуск самый тяжёлый).

## 7. Бэкапы

Ежедневно, 03:20, на VPS:

```bash
20 3 * * * PGPASSWORD='...' /bin/bash /opt/relik/backup-db.sh >> /var/log/relik-backup.log 2>&1
```

Правила:

- дамп лежит в `/var/backups/relik`, хранится 14 дней (`KEEP_DAYS`);
- **раз в квартал** проверять восстановление на пустом проекте:
  `pg_restore --no-owner --no-privileges -d "$TARGET_URL" /var/backups/relik/relik-YYYY-MM-DD.dump`;
- медиа в Storage в дамп не входят — их бэкапят отдельно (Dashboard → Storage
  или `rclone`), иначе восстановите чаты без картинок;
- возраст последнего дампа виден в статусе (строка «Бэкап БД»).

## 8. Деньги: что покупать и когда

| Что | Цена | Когда нужно | Что даёт |
|---|---|---|---|
| Supabase Pro | $25/мес (~2000 ₽) | **сразу, если сервисом пользуются другие люди** | нет паузы, 250 ГБ egress, 8 ГБ БД, 100 ГБ файлов, бэкапы 7 дней, SLA 99,9% |
| Домен `.ru` | ~200–400 ₽/год | для резервного зеркала | свой адрес, независимость от GitHub |
| S3 (Beget/Selectel) | ~150 ₽/мес за 50 ГБ | если медиа > 3–4 ГБ/мес | снимает риск «кончился egress Supabase» |
| VPS 4 vCPU / 8 ГБ | 1500–2500 ₽/мес | только если нужен self-host Supabase | полный контроль, но и вся эксплуатация на вас |

Рекомендация: **Supabase Pro + существующий VPS + внешний монитор**.
Self-host Postgres для приватного мессенджера почти всегда дороже по времени,
чем $25.

### Чек-лист перехода на Pro

1. Dashboard → Organization → Billing → Upgrade to Pro.
2. Settings → Add-ons: бэкапы включены (7 дней) — проверить.
3. После оплаты: `SELECT`-нагрузка не меняется, клиент ничего не замечает.
4. Проверить, что проект больше не помечается Paused в Dashboard.
5. Через месяц — сверить Usage: egress, storage, realtime.

## 9. Обновления и обслуживание

- Деплой сайта: `powershell -ExecutionPolicy Bypass -File C:\67\publish-github.ps1 "..."`.
- Деплой агента: скопировать `scripts/push-service/index.js` на VPS в
  `/opt/relik-push/`, затем `systemctl restart relik-push` и
  `curl -s localhost:8099/healthz`.
- После изменения `sw.js`/ассетов — поднять `VER` в `sw.js` (иначе старый кэш).
- Раз в месяц: открыть статус, посмотреть историю, проверить бэкап, обновить
  зависимости VPS (`apt upgrade`).
- Раз в квартал: restore-тест бэкапа, смена `service_role` ключа и пароля TURN.

## 11. Чего делать нельзя

- Класть `service_role` / secret-ключ в клиентские файлы или в репозиторий.
- Отключать watchdog «чтобы не шумел» — он и есть автоматическое восстановление.
- Считать бэкап существующим, ни разу его не восстановив.
- Включать Supabase Pro и одновременно держать keep-alive, который бьёт в
  проект каждые 5 минут без нужды — лишний egress; при Pro хватает проверок
  агента раз в минуту (они и так есть).
- Переносить базу на свой VPS без ежедневных дампов и проверенного restore.
